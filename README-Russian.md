Общий сервис ответов "AI chat commerce" для экосистемы `aruaru`
(aruaru-tokyo, aruaru-db, e-gov.info, karu.tokyo и т.д). Вместо того,
чтобы каждый сайт реализовывал собственную логику ответов чата, они
обращаются к этому единственному HTTP-сервису — централизуя то
единственное место, которое нужно будет изменить, когда в конечном
итоге будет подключён настоящий вывод LLM.

> ⚠️ **Честное раскрытие (важно, обновлено 2026-07-25)**: с 2026-07-25
> этот сервис интегрирует крейт `opencuda-llm` из `open-cuda` (реальные
> обученные веса GPT-2 124M, `openai-community/gpt2`), поэтому
> `POST /v1/generate` теперь выполняет **настоящую авторегрессионную
> генерацию текста** — утверждение "нет авторегрессионной генерации"
> ниже больше не относится к этому эндпоинту. Тем не менее, **GPT-2
> 124M — это маленькая модель 2019 года, несопоставимая с современными
> коммерческими LLM вроде GPT-4** по возможностям или знаниям. Это
> демонстрация того, что автономная генерация работает без внешнего
> контракта API LLM, а не заявление о качестве уровня state-of-the-art
> — вывод часто грамматически бегло звучит на английском, но не
> гарантированно фактически точен (возможны галлюцинации).
> `POST /v1/chat` (классификация намерений через встраивания
> предложений `opencuda-bert` + косинусное сходство, с 2026-07-21)
> остаётся отдельным, лёгким, быстрым путём для заготовленных ответов —
> намеренно не объединённым с генерацией. Подробности и обоснование
> см. в [CLAUDE.md](CLAUDE.md).

## В паре ("SET") с open-cuda

Зависит через путевую зависимость от крейтов
`opencuda-core`/`opencuda-cpu`/`opencuda-blas`/`opencuda-bert` из
[`open-cuda`](https://github.com/aon-co-jp/open-cuda). При каждом
запросе `/v1/chat` `opencuda-bert` выполняет прямой проход
multilingual-e5-small (вызывая настоящие ядра GEMM/Attention
`opencuda-blas` на `opencuda_cpu::CpuDevice`) для встраивания
сообщения, затем сравнивает его через косинусное сходство с
кэшированным представительным встраиванием каждого намерения. Это
настоящий вызов времени выполнения через вычислительный конвейер
open-cuda, а не просто ссылка в `Cargo.toml` — проверено путём
реального запуска сервера и выполнения `POST /v1/chat`.

При этом это не настоящий нейронный вывод LLM (генерация диалога) —
только прямой проход энкодера; авторегрессионный декодер остаётся
нереализованным. Специфичные для GPU быстрые пути
(`GemmPath::CuBlas`/`RocBlas`/`OneMkl`) всё ещё являются заглушками
(пути CPU и универсального Vulkan реализованы). Подробности см. в
разделе HANDOFF `CLAUDE.md` open-cuda.

**Обновление 2026-07-25 (резервный откат по доступности)**: если
`models/multilingual-e5-small/` (470МБ+) отсутствует или не удаётся
загрузить, этот сервис теперь автоматически откатывается к исходному
скалярному произведению bag-of-words (`src/bow_fallback.rs`) вместо
полного отказа запросов. Поле `engine` в ответе `/v1/chat` всегда
честно сообщает, какой путь был фактически использован
(`embedding-cosine-v0-opencuda-bert-cpu` или
`bow-dotproduct-v0-opencuda-cpu-fallback`) — качество классификации
заметно ниже на резервном пути (сопоставление ключевых слов, а не
семантическое понимание).

## API

- `POST /v1/chat` — `{"message": "...", "tenant": "..."(опционально)}`
  → `{"reply": "...", "engine": "...", "matched_intent": "..."}`
  (классификация намерений, лёгкие/быстрые заготовленные ответы)
- `POST /v1/generate` — `{"prompt": "...", "max_new_tokens":
  16(опционально, по умолчанию 16, максимум 128), "tenant":
  "..."(опционально)}` → `{"completion": "...", "engine":
  "gpt2-124m-greedy-decode-v0-opencuda-llm-cpu", "disclosure": "..."}`
  (настоящая авторегрессионная генерация с помощью весов GPT-2 124M —
  тяжелее, но подлинная. **Штраф за повторение по умолчанию `1.3`** —
  переменная `ARUARU_LLM_REPETITION_PENALTY` для переопределения,
  `1.0` отключает его — чтобы предотвратить бесконечные циклы
  повторения. Рекомендуются подсказки на английском, так как
  BPE-словарь GPT-2 обучен в основном на английском тексте. Пример,
  проверенный сквозным образом через реальный HTTP:
  `{"prompt": "The quick brown fox", "max_new_tokens": 16}` →
  `"completion": "es are a great way to get a little bit of a kick out
  of your"`)
- `GET /v1/models/catalog` — доступные для установки совместимые с
  GPT-2 модели (`gpt2`/`distilgpt2`/`gpt2-medium`/`gpt2-large`/
  `gpt2-xl`, последняя добавлена 2026-07-27), какие уже установлены, и
  каталог текущей активной модели.
- `POST /v1/models/install` / `POST /v1/models/select` — загрузить
  модель из каталога с Hugging Face, и горячо переключить активную
  модель без перезапуска процесса.
- `GET /v1/recommend` (добавлено 2026-07-27) — обнаруживает
  оборудование (VRAM) через `open-cuda` (Vulkan) или `open-directx`
  (DXGI) и возвращает рекомендуемый размер модели семейства GPT-2, не
  загружая ничего.
- `POST /v1/recommend-and-download` (добавлено 2026-07-27,
  поддерживает кнопку "Download recommended LLM") — обнаруживает
  оборудование → выбирает рекомендуемый размер → загружает его с
  Hugging Face, если ещё не присутствует (идемпотентно) → горячо
  переключает `/v1/generate` на его использование. Возвращает
  `{"recommendation": {...}, "already_installed":bool,
  "switched_to_recommended":bool, "message_ja":"..."}`.
- `GET /` (добавлено 2026-07-27) — минимальный статический HTML UI
  (`static/index.html`, без фреймворка) с одной кнопкой "Download
  recommended LLM", отображением прогресса, и панелью тестирования
  генерации после переключения.
- `POST /admin/tenants` / `GET /admin/tenants` /
  `DELETE /admin/tenants/:host` — управление регистрацией арендаторов
  (аутентификация через заголовок `x-admin-token`)
- `GET /healthz` — проверка работоспособности

### Обнаружение оборудования → рекомендуемый размер LLM (добавлено 2026-07-27)

`src/hardware.rs` реализует простую эвристику, которая выбирает размер
семейства GPT-2 (124M/355M/774M/1.5B) по обнаруженной VRAM: <2ГБ →
124M, 2-4ГБ → 355M, 4-8ГБ → 774M, 8ГБ+ → 1.5B; неопределяемый GPU /
только CPU → 124M (безопасный резерв). **Честное раскрытие**: это
грубое сравнение размера и VRAM (количество параметров × 4 байта,
оценка fp32), а не точная модель производительности — она игнорирует
память KV-кэша и активаций.

Обнаружение GPU опционально через фичи Cargo `hw-detect-vulkan` /
`hw-detect-directx` (по умолчанию отключены, чтобы сборки только для
CPU или кросс-компилируемые сборки не были вынуждены зависеть от
загрузчика Vulkan / Windows SDK). При включении предпочтение отдаётся
Vulkan; если включены обе фичи, результат DXGI (DirectX) сверяется с
результатом Vulkan и логируется (`cross_check_agreement`).
**Проверено на реальном оборудовании**: при запуске с
`--features hw-detect-vulkan` на NVIDIA GeForce GT 730 этой машины
было сообщено `vram_bytes=2104819712` — точно совпадающее со
значением, ранее зафиксированным через DXGI в `CLAUDE.md` `open-cuda`,
подтверждая, что оба пути обнаружения согласуются по этому GPU.

### Выгрузка KV-кэша/весов в стиле DeepSeek "Engram": исследовано и отклонено (2026-08-08)

Мы исследовали, может ли техника DeepSeek "Engram" — вытеснение
статических знаний (KV-кэш или фрагменты весов) из VRAM в системную
RAM и перезагрузка по требованию — помочь этому сервису работать на
GPU с малым объёмом VRAM, таких как GT 730. **После прочтения реального
кода мы отказались от реализации** — не потому что это сложно, а
потому что путь вывода `open-cuda`, от которого зависит этот репозиторий,
изначально не имеет резидентного в VRAM состояния для вытеснения.
Каждая диспетчеризация GEMM/Attention/softmax в `opencuda-blas` (то
есть каждый вызов `sgemm`, идущий в Vulkan) выделяет буфер VRAM через
RAII-хранителя `ScopedAlloc` (`opencuda-blas/src/lib.rs`), копирует
хост→устройство, вычисляет, копирует устройство→хост, и немедленно
освобождает — ничего не остаётся в VRAM после возврата вызова. И веса
GPT-2 (`word_embeddings` `GptModel` и `Linear` каждого слоя), и
KV-кэш (`k`/`v`/`k_latent`/`v_latent` из
`open-cuda-llm::KvCacheHead`) являются обычными `Vec<f32>`, живущими
в системной RAM на протяжении всего своего срока жизни, даже при
запуске с `--features real-vulkan`. Другими словами, эта архитектура
уже находится — случайно по замыслу, а не намеренно — в состоянии, к
которому стремится Engram: состояние постоянно остаётся резидентным в
системной RAM, а GPU затрагивается только временно, для каждой
операции. Добавление слоя LRU-вытеснения поверх этого не имело бы
ничего для вытеснения, поэтому не было бы никакого измеримого эффекта
для отчёта (мы не собираемся заявлять о выгоде, которую не можем
измерить). Подробности точных прочитанных путей кода см. в записи
HANDOFF от 2026-08-08 в CLAUDE.md.

### Классификация против генерации — что использовать

`/v1/chat` (классификация) и `/v1/generate` (генерация) служат разным
целям и намеренно не объединены: `/v1/chat` только направляет к
заготовленным ответам и является лёгким/быстрым (единственный прямой
проход встраивания); `/v1/generate` запускает полную модель GPT-2 124M
(548МБ весов) и тяжелее, но производит подлинный свободный текст.
Выбирайте то, что подходит для случая использования.

## Архитектура "теневого клона" (分身の術)

Следуя тому же дизайну, что и `open-web-server`: один запущенный
экземпляр совместно используется несколькими доменами, без требования
установки для каждого домена. Управление предполагается осуществлять
из [open-easy-web](https://github.com/aon-co-jp/open-easy-web) (эта
интеграция ещё не подключена). Подробности см. в
[CLAUDE.md](CLAUDE.md).

## Технологический стек

Rust + [RPoem](https://github.com/aon-co-jp/RPoem)
(`open-runo-poem-compat`, фасад, совместимый с API Poem, реализованный
непосредственно поверх tokio/hyper — без зависимости от настоящего
крейта [Poem](https://github.com/poem-web/poem), перенесено
2026-07-31) + [open-cuda](https://github.com/aon-co-jp/open-cuda). Нет
зависимости от БД, единый самодостаточный бинарник. Может
использоваться из Rust или любого другого языка через обычный HTTP
(этот сервис является HTTP-фасадом обслуживания для Rust-портов
Python-библиотек ИИ — `opencuda-bert`/`opencuda-llm`/
`opencuda-whisper`, то есть эквивалентов Transformers/vLLM/Whisper).

См. [CLAUDE.md](CLAUDE.md) (только на японском) для философии дизайна
и [PORTING.md](PORTING.md) (только на японском) о том, как переносить
эти паттерны в другие места.

## Установка

С 2026-07-23 добавлены `install.sh` (Linux, регистрирует службу
systemd), `install.ps1` (Windows, выводит шаги регистрации службы
Windows), и `.github/workflows/release.yml` (собирает бинарники Linux
x86_64 / Windows x86_64 при каждом пуше тега и прикрепляет их к
[GitHub Releases](https://github.com/aon-co-jp/aruaru-llm/releases)).
**Честное раскрытие**: при запуске этому бинарнику нужны веса модели
`multilingual-e5-small` (470МБ+, Hugging Face, лицензия MIT),
получаемые отдельно — не входят в установщик по лицензионным
причинам; см. `install.sh`/`install.ps1` для команды загрузки. Сборка
имеет соседнюю путевую зависимость от `../open-cuda`, поэтому сборка
из исходного кода требует клонирования `open-cuda` в соседний каталог
(CI делает это автоматически через `release.yml`). **Добавлено
2026-07-25**: `/v1/generate` (генерация GPT-2 124M) дополнительно
требует `config.json` / `model.safetensors` (548МБ) /
`tokenizer.json` (`openai-community/gpt2`, с Hugging Face) в
`../open-cuda/crates/opencuda-llm/models/gpt2/` (переопределите путь
переменной окружения `ARUARU_LLM_GPT2_DIR`). При отсутствии только
`/v1/generate` возвращает 503 — `/v1/chat` и остальная часть сервиса
продолжают работать нормально (дизайн с приоритетом доступности, та
же философия, что и у `bow_fallback`).

```
curl -fsSL https://github.com/aon-co-jp/aruaru-llm/releases/latest/download/aruaru-llm-linux-x86_64.tar.gz | tar xz
sudo ./install.sh
```
