# Философия дизайна, политика разработки и правила среды разработки (aruaru-llm)

> **Примечание**: это сжатый перевод текущего состояния. Подробный
> исторический журнал HANDOFF (десятки записей) для краткости
> остаётся доступен только на японском в [CLAUDE.md](CLAUDE.md) — там
> смотрите детали по каждой сессии.

Репозиторий GitHub: [aon-co-jp/aruaru-llm](https://github.com/aon-co-jp/aruaru-llm).

## Роль этого проекта

Общий, автономный HTTP-сервис, предоставляющий логику ответов
«AI chat commerce» для экосистемы `aruaru` (aruaru-tokyo, aruaru-db,
e-gov.info, karu.tokyo и т. д.). Вместо того чтобы каждый сайт
реализовывал собственную логику ответов чата, все они обращаются к
этому единому сервису по HTTP — так место, которое нужно будет
изменить при будущем переходе на настоящий вывод LLM, остаётся
централизованным в одном месте.

## Честное раскрытие (важно)

С 2026-07-25 `/v1/generate` использует crate `opencuda-llm` из
`open-cuda` (реальные обученные веса GPT-2 124M,
`openai-community/gpt2`) для **настоящей авторегрессивной генерации
текста**. Однако GPT-2 124M — небольшая модель 2019 года, несравнимая
с современными коммерческими LLM вроде GPT-4 ни по возможностям, ни по
знаниям. `/v1/chat` (классификация намерений) остаётся отдельным:
`opencuda-bert` (multilingual-e5-small) вычисляет реальные эмбеддинги
предложений и классифицирует по косинусному сходству с
репрезентативными векторами намерений — это **классификация
семантического сходства на основе энкодера**, а не генерация диалога.
Обе возможности намеренно не объединены.

## Текущая поверхность API

- `POST /v1/chat` — `{"message": "...", "tenant": "..."(опционально)}` →
  `{"reply": "...", "engine": "embedding-cosine-v0-opencuda-bert-cpu",
  "matched_intent": "..."}`.
- `POST /v1/generate` — `{"prompt": "...", "max_new_tokens":
  16(опционально, по умолчанию 16, максимум 128), "tenant":
  "..."(опционально)}` → `{"completion": "...", "engine":
  "gpt2-124m-greedy-decode-v0-opencuda-llm-cpu", "disclosure": "..."}`.
  Если реальных весов GPT-2 нет, честно возвращается `503` (без
  тихого отката, как у `/v1/chat`).
- `POST /admin/tenants` / `GET /admin/tenants` /
  `DELETE /admin/tenants/:host` — динамическое управление арендаторами
  (аутентификация через заголовок `x-admin-token`).
- `GET /healthz` — проверка состояния.

### Новое: `POST /v1/generate-speculative` (добавлено 2026-08-17, коммит `8f08900`)

Безлотерейное спекулятивное декодирование в стиле DSpark через
`open-cuda-llm::GptModel::generate_speculative`, **опционально**
(НЕ заменяет стандартный `/v1/generate`). Принимает `draft_id`,
указывающий на уже загруженную модель из каталога (например,
`"distilgpt2"`) в качестве черновой модели. **Критическое честное
раскрытие**: при выполнении на CPU в `open-cuda` было измерено, что
этот путь **медленнее**, чем обычный `generate()`, даже при 80%
доле принятия — потому что наивный CPU-GEMM почти не имеет
накладных расходов на диспетчеризацию, которые можно было бы устранить,
поэтому дополнительные вычисления черновой модели на CPU дают чистый
убыток. Проверка скорости под `real-vulkan` (где накладные расходы на
диспетчеризацию доминируют — реально предполагаемый сценарий
использования) ещё не проводилась. Также раскрыто: штраф за повтор и
модели, сжатые MLA, этим спекулятивным путём не поддерживаются.

## Технологический стек

Rust + [RPoem](https://github.com/aon-co-jp/RPoem)
(`open-runo-poem-compat`, фасад, совместимый с API Poem, реализованный
напрямую поверх tokio/hyper, с 2026-07-31 вместо настоящего crate
[Poem](https://github.com/poem-web/poem) — нет экстрактора `Data<T>`,
общее состояние захватывается через closure `Arc::clone` при
регистрации маршрутов) + [open-cuda](https://github.com/aon-co-jp/open-cuda).
Нет зависимости от БД, единый автономный бинарник.

## Архитектура «теневого клона» (分身の術)

Как и `open-web-server`: один запущенный экземпляр совместно
используется несколькими доменами без необходимости установки на
каждый домен (`TenantRegistry` в `src/tenants.rs`, регистрация во
время выполнения без перезапуска через API `/admin/tenants`).
Управление предполагается со стороны
[open-easy-web](https://github.com/aon-co-jp/open-easy-web) (интеграция
пока не подключена).
