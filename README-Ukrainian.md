Спільний сервіс відповідей "AI chat commerce" для екосистеми `aruaru`
(aruaru-tokyo, aruaru-db, e-gov.info, karu.tokyo тощо). Замість того,
щоб кожен сайт реалізовував власну логіку відповідей чату, вони
звертаються до цього єдиного HTTP-сервісу — централізуючи те єдине
місце, яке потрібно буде змінити, коли врешті буде підключено
справжній вивід LLM.

> ⚠️ **Чесне розкриття (важливо, оновлено 2026-07-25)**: з 2026-07-25
> цей сервіс інтегрує крейт `opencuda-llm` з `open-cuda` (реальні
> навчені ваги GPT-2 124M, `openai-community/gpt2`), тому
> `POST /v1/generate` тепер виконує **справжню авторегресивну
> генерацію тексту** — твердження "немає авторегресивної генерації"
> нижче більше не стосується цього ендпоінту. Проте **GPT-2 124M — це
> маленька модель 2019 року, непорівнянна із сучасними комерційними
> LLM на кшталт GPT-4** за можливостями чи знаннями. Це демонстрація
> того, що автономна генерація працює без зовнішнього контракту API
> LLM, а не заява про якість рівня state-of-the-art — вивід часто
> граматично плавно звучить англійською, але не гарантовано фактично
> точний (можливі галюцинації). `POST /v1/chat` (класифікація намірів
> через вбудовування речень `opencuda-bert` + косинусна подібність, з
> 2026-07-21) залишається окремим, легким, швидким шляхом для
> заготовлених відповідей — навмисно не об'єднаним із генерацією.
> Подробиці та обґрунтування див. у [CLAUDE.md](CLAUDE.md).

## У парі ("SET") з open-cuda

Залежить через шляхову залежність від крейтів
`opencuda-core`/`opencuda-cpu`/`opencuda-blas`/`opencuda-bert` з
[`open-cuda`](https://github.com/aon-co-jp/open-cuda). При кожному
запиті `/v1/chat` `opencuda-bert` виконує прямий прохід
multilingual-e5-small (викликаючи справжні ядра GEMM/Attention
`opencuda-blas` на `opencuda_cpu::CpuDevice`) для вбудовування
повідомлення, потім порівнює його через косинусну подібність із
кешованим репрезентативним вбудовуванням кожного наміру. Це справжній
виклик часу виконання через обчислювальний конвеєр open-cuda, а не
просто посилання в `Cargo.toml` — перевірено шляхом реального запуску
сервера та виконання `POST /v1/chat`.

При цьому це не справжній нейронний вивід LLM (генерація діалогу) —
лише прямий прохід енкодера; авторегресивний декодер залишається
нереалізованим. Специфічні для GPU швидкі шляхи
(`GemmPath::CuBlas`/`RocBlas`/`OneMkl`) досі є заглушками (шляхи CPU
та загального Vulkan реалізовані). Подробиці див. у розділі HANDOFF
`CLAUDE.md` open-cuda.

**Оновлення 2026-07-25 (резервне перемикання за доступністю)**: якщо
`models/multilingual-e5-small/` (470МБ+) відсутній або не вдається
завантажити, цей сервіс тепер автоматично переходить на вихідний
скалярний добуток bag-of-words (`src/bow_fallback.rs`) замість повної
відмови запитів. Поле `engine` у відповіді `/v1/chat` завжди чесно
повідомляє, який шлях був фактично використаний
(`embedding-cosine-v0-opencuda-bert-cpu` або
`bow-dotproduct-v0-opencuda-cpu-fallback`) — якість класифікації
помітно нижча на резервному шляху (зіставлення ключових слів, а не
семантичне розуміння).

## API

- `POST /v1/chat` — `{"message": "...", "tenant": "..."(опційно)}` →
  `{"reply": "...", "engine": "...", "matched_intent": "..."}`
  (класифікація намірів, легкі/швидкі заготовлені відповіді)
- `POST /v1/generate` — `{"prompt": "...", "max_new_tokens":
  16(опційно, за замовчуванням 16, максимум 128), "tenant":
  "..."(опційно)}` → `{"completion": "...", "engine":
  "gpt2-124m-greedy-decode-v0-opencuda-llm-cpu", "disclosure": "..."}`
  (справжня авторегресивна генерація за допомогою ваг GPT-2 124M —
  важче, але справжня. **Штраф за повторення за замовчуванням `1.3`**
  — змінна `ARUARU_LLM_REPETITION_PENALTY` для перевизначення, `1.0`
  вимикає його — щоб запобігти нескінченним циклам повторення.
  Рекомендуються запити англійською, оскільки BPE-словник GPT-2
  навчений переважно на англійському тексті. Приклад, перевірений
  наскрізно через реальний HTTP:
  `{"prompt": "The quick brown fox", "max_new_tokens": 16}` →
  `"completion": "es are a great way to get a little bit of a kick out
  of your"`)
- `GET /v1/models/catalog` — доступні для встановлення сумісні з
  GPT-2 моделі (`gpt2`/`distilgpt2`/`gpt2-medium`/`gpt2-large`/
  `gpt2-xl`, остання додана 2026-07-27), які вже встановлені, і
  каталог поточної активної моделі.
- `POST /v1/models/install` / `POST /v1/models/select` — завантажити
  модель із каталогу з Hugging Face, та гаряче перемкнути активну
  модель без перезапуску процесу.
- `GET /v1/recommend` (додано 2026-07-27) — виявляє обладнання (VRAM)
  через `open-cuda` (Vulkan) або `open-directx` (DXGI) і повертає
  рекомендований розмір моделі родини GPT-2, нічого не завантажуючи.
- `POST /v1/recommend-and-download` (додано 2026-07-27, підтримує
  кнопку "Download recommended LLM") — виявляє обладнання → обирає
  рекомендований розмір → завантажує його з Hugging Face, якщо ще не
  присутній (ідемпотентно) → гаряче перемикає `/v1/generate` на його
  використання. Повертає `{"recommendation": {...},
  "already_installed":bool, "switched_to_recommended":bool,
  "message_ja":"..."}`.
- `GET /` (додано 2026-07-27) — мінімальний статичний HTML UI
  (`static/index.html`, без фреймворку) з однією кнопкою "Download
  recommended LLM", відображенням прогресу, та панеллю тестування
  генерації після перемикання.
- `POST /admin/tenants` / `GET /admin/tenants` /
  `DELETE /admin/tenants/:host` — керування реєстрацією орендарів
  (автентифікація через заголовок `x-admin-token`)
- `GET /healthz` — перевірка працездатності

### Виявлення обладнання → рекомендований розмір LLM (додано 2026-07-27)

`src/hardware.rs` реалізує просту евристику, яка обирає розмір родини
GPT-2 (124M/355M/774M/1.5B) на основі виявленої VRAM: <2ГБ → 124M,
2-4ГБ → 355M, 4-8ГБ → 774M, 8ГБ+ → 1.5B; невизначуваний GPU / лише CPU
→ 124M (безпечний резерв). **Чесне розкриття**: це грубе порівняння
розміру та VRAM (кількість параметрів × 4 байти, оцінка fp32), а не
точна модель продуктивності — вона ігнорує пам'ять KV-кешу та
активацій.

Виявлення GPU є опційним через фічі Cargo `hw-detect-vulkan` /
`hw-detect-directx` (вимкнені за замовчуванням, щоб збірки лише для
CPU або крос-компільовані збірки не були змушені залежати від
завантажувача Vulkan / Windows SDK). При увімкненні перевага надається
Vulkan; якщо увімкнено обидві фічі, результат DXGI (DirectX)
звіряється з результатом Vulkan і логується
(`cross_check_agreement`). **Перевірено на реальному обладнанні**: під
час запуску з `--features hw-detect-vulkan` на NVIDIA GeForce GT 730
цієї машини було повідомлено `vram_bytes=2104819712` — точно
збігається зі значенням, раніше зафіксованим через DXGI в
`CLAUDE.md` `open-cuda`, підтверджуючи, що обидва шляхи виявлення
узгоджуються щодо цього GPU.

### Вивантаження KV-кешу/ваг у стилі DeepSeek "Engram": досліджено та відхилено (2026-08-08)

Ми дослідили, чи могла б техніка DeepSeek "Engram" — витіснення
статичних знань (KV-кеш або фрагменти ваг) із VRAM у системну RAM та
перезавантаження за потреби — допомогти цьому сервісу працювати на
GPU з малим обсягом VRAM, таких як GT 730. **Прочитавши реальний код,
ми відмовилися від реалізації** — не тому, що це складно, а тому, що
шлях виведення `open-cuda`, від якого залежить цей репозиторій,
спершу не має резидентного у VRAM стану для витіснення. Кожна
диспетчеризація GEMM/Attention/softmax в `opencuda-blas` (тобто кожен
виклик `sgemm`, що йде до Vulkan) виділяє буфер VRAM через
RAII-охоронця `ScopedAlloc` (`opencuda-blas/src/lib.rs`), копіює
хост→пристрій, обчислює, копіює пристрій→хост, і негайно звільняє —
нічого не залишається у VRAM після завершення виклику. І ваги GPT-2
(`word_embeddings` `GptModel` та `Linear` кожного шару), і KV-кеш
(`k`/`v`/`k_latent`/`v_latent` з `open-cuda-llm::KvCacheHead`) є
звичайними `Vec<f32>`, які живуть у системній RAM протягом усього
свого життєвого циклу, навіть під час запуску з `--features
real-vulkan`. Іншими словами, ця архітектура вже перебуває —
випадково за задумом, а не навмисно — у стані, до якого прагне
Engram: стан постійно залишається резидентним у системній RAM, а GPU
торкається лише тимчасово, для кожної операції. Додавання шару
LRU-витіснення поверх цього не мало б нічого для витіснення, тому не
було б жодного вимірюваного ефекту для звіту (ми не збираємося
заявляти про вигоду, яку не можемо виміряти). Подробиці точних
прочитаних шляхів коду див. у записі HANDOFF від 2026-08-08 в
CLAUDE.md.

### Класифікація проти генерації — що використовувати

`/v1/chat` (класифікація) та `/v1/generate` (генерація) слугують
різним цілям і навмисно не об'єднані: `/v1/chat` лише спрямовує до
заготовлених відповідей і є легким/швидким (єдиний прямий прохід
вбудовування); `/v1/generate` запускає повну модель GPT-2 124M
(548МБ ваг) і важчий, але виробляє справжній вільний текст. Оберіть
те, що підходить для вашого випадку використання.

## Технологічний стек

Rust + [RPoem](https://github.com/aon-co-jp/RPoem)
(`open-runo-poem-compat`, фасад, сумісний із API Poem, реалізований
безпосередньо поверх tokio/hyper — без залежності від справжнього
крейта [Poem](https://github.com/poem-web/poem), перенесено
2026-07-31) + [open-cuda](https://github.com/aon-co-jp/open-cuda).
Немає залежності від БД, єдиний самодостатній бінарник. Може
використовуватися з Rust або будь-якої іншої мови через звичайний
HTTP (цей сервіс є HTTP-фасадом обслуговування для Rust-портів
Python-бібліотек ШІ — `opencuda-bert`/`opencuda-llm`/
`opencuda-whisper`, тобто еквівалентів Transformers/vLLM/Whisper).

Див. [CLAUDE.md](CLAUDE.md) (лише японською) щодо філософії дизайну та
[PORTING.md](PORTING.md) (лише японською) про те, як переносити ці
патерни в інші місця.

## Встановлення

З 2026-07-23 додано `install.sh` (Linux, реєструє службу systemd),
`install.ps1` (Windows, виводить кроки реєстрації служби Windows), та
`.github/workflows/release.yml` (збирає бінарники Linux x86_64 /
Windows x86_64 за кожного пушу тегу та прикріплює їх до
[GitHub Releases](https://github.com/aon-co-jp/aruaru-llm/releases)).
**Чесне розкриття**: під час запуску цьому бінарнику потрібні ваги
моделі `multilingual-e5-small` (470МБ+, Hugging Face, ліцензія MIT),
що отримуються окремо — не входять до встановлювача з ліцензійних
причин; див. `install.sh`/`install.ps1` щодо команди завантаження.
Збірка має суміжну шляхову залежність від `../open-cuda`, тому
збирання з вихідного коду вимагає клонування `open-cuda` до сусіднього
каталогу (CI робить це автоматично через `release.yml`). **Додано
2026-07-25**: `/v1/generate` (генерація GPT-2 124M) додатково потребує
`config.json` / `model.safetensors` (548МБ) / `tokenizer.json`
(`openai-community/gpt2`, з Hugging Face) у
`../open-cuda/crates/opencuda-llm/models/gpt2/` (перевизначте шлях
змінною середовища `ARUARU_LLM_GPT2_DIR`). За відсутності лише
`/v1/generate` повертає 503 — `/v1/chat` та решта сервісу продовжують
працювати нормально (дизайн з пріоритетом доступності, та сама
філософія, що й у `bow_fallback`).

```
curl -fsSL https://github.com/aon-co-jp/aruaru-llm/releases/latest/download/aruaru-llm-linux-x86_64.tar.gz | tar xz
sudo ./install.sh
```
