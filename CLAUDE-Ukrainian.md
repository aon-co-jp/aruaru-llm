# Філософія дизайну, політика розробки та правила середовища розробки (aruaru-llm)

> **Примітка**: це стислий переклад поточного стану. Детальний
> історичний журнал HANDOFF (десятки записів) для стислості
> залишається доступним лише японською в [CLAUDE.md](CLAUDE.md) —
> дивіться там деталі по кожній сесії.

Репозиторій GitHub: [aon-co-jp/aruaru-llm](https://github.com/aon-co-jp/aruaru-llm).

## Роль цього проєкту

Спільний, автономний HTTP-сервіс, що надає логіку відповідей
«AI chat commerce» для екосистеми `aruaru` (aruaru-tokyo, aruaru-db,
e-gov.info, karu.tokyo тощо). Замість того щоб кожен сайт реалізовував
власну логіку відповідей чату, всі вони звертаються до цього єдиного
сервісу через HTTP — централізуючи місце, яке потрібно буде змінити
при майбутньому переході на справжній вивід LLM.

## Чесне розкриття (важливо)

З 2026-07-25 `/v1/generate` використовує crate `opencuda-llm` з
`open-cuda` (реальні навчені ваги GPT-2 124M,
`openai-community/gpt2`) для **справжньої авторегресивної генерації
тексту**. Проте GPT-2 124M — невелика модель 2019 року, непорівнянна
із сучасними комерційними LLM на кшталт GPT-4 ні за можливостями, ні
за знаннями. `/v1/chat` (класифікація намірів) залишається окремим:
`opencuda-bert` (multilingual-e5-small) обчислює реальні ембедінги
речень і класифікує за косинусною подібністю з репрезентативними
векторами намірів — це **класифікація семантичної подібності на
основі енкодера**, а не генерація діалогу. Обидві можливості
навмисно не об'єднані.

## Поточна поверхня API

- `POST /v1/chat` — `{"message": "...", "tenant": "..."(опційно)}` →
  `{"reply": "...", "engine": "embedding-cosine-v0-opencuda-bert-cpu",
  "matched_intent": "..."}`.
- `POST /v1/generate` — `{"prompt": "...", "max_new_tokens":
  16(опційно, за замовчуванням 16, максимум 128), "tenant":
  "..."(опційно)}` → `{"completion": "...", "engine":
  "gpt2-124m-greedy-decode-v0-opencuda-llm-cpu", "disclosure": "..."}`.
  Якщо справжніх ваг GPT-2 немає, чесно повертається `503` (без
  тихого відкату, як у `/v1/chat`).
- `POST /admin/tenants` / `GET /admin/tenants` /
  `DELETE /admin/tenants/:host` — динамічне керування орендарями
  (автентифікація через заголовок `x-admin-token`).
- `GET /healthz` — перевірка стану.

### Нове: `POST /v1/generate-speculative` (додано 2026-08-17, коміт `8f08900`)

Безвтратне спекулятивне декодування в стилі DSpark через
`open-cuda-llm::GptModel::generate_speculative`, **опційно**
(НЕ замінює стандартний `/v1/generate`). Приймає `draft_id`, що
вказує на вже завантажену модель з каталогу (наприклад,
`"distilgpt2"`) як чорнову модель. **Критичне чесне розкриття**: під
час виконання на CPU в `open-cuda` було виміряно, що цей шлях
**повільніший**, ніж звичайний `generate()`, навіть при 80% рівні
прийняття — бо наївний CPU-GEMM майже не має накладних витрат на
диспетчеризацію, які можна було б усунути, тож додаткові обчислення
чорнової моделі на CPU дають чисту втрату. Перевірка швидкості під
`real-vulkan` (де накладні витрати на диспетчеризацію домінують —
справді передбачуваний сценарій використання) ще не проводилась.
Також розкрито: штраф за повторення та моделі, стиснені MLA, цим
спекулятивним шляхом не підтримуються.

## Технологічний стек

Rust + [RPoem](https://github.com/aon-co-jp/RPoem)
(`open-runo-poem-compat`, фасад, сумісний з API Poem, реалізований
безпосередньо поверх tokio/hyper, з 2026-07-31 замість справжнього
crate [Poem](https://github.com/poem-web/poem) — немає екстрактора
`Data<T>`, спільний стан захоплюється через closure `Arc::clone` при
реєстрації маршрутів) + [open-cuda](https://github.com/aon-co-jp/open-cuda).
Немає залежності від БД, єдиний автономний бінарник.

## Архітектура «тіньового клону» (分身の術)

Як і `open-web-server`: один запущений екземпляр спільно
використовується кількома доменами без потреби встановлення на кожен
домен (`TenantRegistry` у `src/tenants.rs`, реєстрація під час
виконання без перезапуску через API `/admin/tenants`). Керування
передбачається з боку
[open-easy-web](https://github.com/aon-co-jp/open-easy-web) (інтеграція
ще не підключена).
